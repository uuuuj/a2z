### 이벤트 핸들러의 매개변수 — `object sender` · `EventArgs e`

```csharp

//                                       ──┬──  ──┬──  ────┬───  ┬
//                                        타입    이름     타입   이름
```

- **`sender`** = 눌린 **버튼 객체 그 자체**. `object` 는 타입 이름일 뿐
- **`e`** = 그 이벤트에 딸려 온 정보
- 버튼 객체는 **창이 만들어질 때 이미 생성**돼 있다 (`Form1.Designer.cs:479~483`).
  누르는 순간 새로 만들어지는 게 아니라 **있던 객체를 넘겨준다**
- 객체는 복사되지 않고 **자리(참조)만 넘어간다** → `sender.Enabled` 를 바꾸면 원본 버튼이 바뀐다

**"보낸다"의 뜻** — 우편이 아니라 **함수를 부르며 인자로 건네는 것**.
우리가 `ProcessSingleStruFull(stru, saveDir)` 하는 것과 같고, **부르는 주체가 WinForms 일 뿐**이다.

**왜 `sender` 를 주나** — 「눌렸다」는 함수가 불린 사실 자체로 전달된다.
`sender` 는 **「어느 것이 눌렸나」**에 답하는 값이다. 버튼 여러 개를 한 함수에 걸었을 때 필요하다.

🔴 **실측 — 이 코드베이스는 전부 1:1 배선이다.** 한 핸들러가 여러 컨트롤에 걸린 경우 0건.
그래서 **`sender` 는 선언 줄 말고 사용 0건.** 핸들러 53개가 전부 받기만 한다.

### `Click` 의 `e` 는 빈 객체가 아니다

디버거로 보면 `e` 에 `X=92 Y=14 Button=Left` 가 들어 있다.
선언은 `EventArgs` 인데 **실제로 들어온 물건은 `MouseEventArgs`** — 자식 타입이라 그 자리에 들어간다.

- 좌표 기준은 화면이 아니라 **그 버튼의 왼쪽 위(0,0)**.
  `btnExtractDrawingList` 는 `120 × 28` (`Designer.cs:481`) 이라 `(92,14)` 는 버튼 안 오른쪽 3/4 지점
- **키보드로 누르면 다르다** — Tab 으로 포커스 후 Space/Enter 면 `e` 는 정보 없는 `EventArgs`
- 그래서 `(MouseEventArgs)e` 로 캐스팅하면 **키보드 입력에서 예외**가 난다.
  쓰려면 `e as MouseEventArgs` + null 검사

| `Click` | `MouseEventArgs` 또는 `EventArgs` | 좌표·버튼 / 없음 | 안 씀 |

### 속성(property) 과 getter

**겉은 변수인데 실제로는 함수가 도는 것.** `MfgDrawing.cs:3634~3643` 에 필드와 속성이 나란히 있다.

```csharp

public double TotalLength;    // 필드

public MfgAxisVector Direction                       // 속성 — 읽는 순간 계산이 돈다

```

- **getter** = 읽을 때 도는 함수 (`get { }`) · **setter** = 넣을 때 도는 함수 (`set { }`)
- `Models.cs` 의 `{ get; set; }` 는 **자동 속성** — 컴파일러가 상자와 함수를 알아서 만든다. 사실상 필드
- **괄호가 구분점** — `()` 가 붙으면 메서드. 안 붙으면 필드 아니면 속성(선언을 봐야 구분)
- ⚠ **속성은 읽기만 해도 코드가 돈다.** 조사식에 넣으면 그 자리에서 실행된다
  (이 코드는 `Models.cs` 107개가 전부 자동 속성이고, 계산이 든 건 `MfgDrawing.cs` 3 · `DrawingSheets.cs` 5)

### 재진입 가드 — 왜 버튼을 꺼도 플래그가 또 필요한가

`_p2aInProgress` 는 **「지금 일괄 출력이 도는 중인가」를 적어둔 쪽지 한 장**이다. 세 지점이 한 짝.

```
53   private bool _p2aInProgress = false;   선언 (프로그램 시작 = 안 돎)
517  if (_p2aInProgress) return;            읽기 — 이미 돌면 나간다
568  _p2aInProgress = true;                 쓰기 — 문을 잠근다
745  _p2aInProgress = false;                finally 안 — 문을 연다
```

**517 을 통과했다는 건 이미 `false` 였다는 뜻**이라, 568 에서 `true` 로 바꿔도 자기 자신은 안 걸린다.
이미 지나온 문이다. `true` 는 「멈춤」이 아니라 **「다음 사람이 못 들어옴」**이다.

**570 에서 버튼을 껐는데도 쪽지가 필요한 이유** — *이미 큐에 들어간 클릭* 때문이다.

```
09:00:00.0  클릭 → 핸들러 시작
09:00:00.1  사용자가 한 번 더 클릭        → 메시지 큐에 쌓임
09:00:00.2  570: 버튼 Enabled = false     ← 늦었다. 큐에 이미 하나 있다
09:00:05.0  669: Application.DoEvents()   → 큐에 있던 클릭이 지금 처리됨
                 → 핸들러 재진입 → 517 이 잡아낸다  ✋
```

버튼 끄기는 **앞으로의 클릭**을, 플래그는 **이미 줄 서 있는 클릭**을 막는다.
`Application.DoEvents()` 를 20곳에서 쓰는 이 코드에선 플래그가 없으면 뚫린다.

### 메시지 루프 — 이 프로그램이 도는 방식

WinForms 프로그램은 **무한 루프 하나**로 돈다. `Application.Run(new Form1())` 이 그 루프다.

```
while (프로그램이 살아있는 동안)
{
    큐에서 메시지 하나 꺼낸다      "왼쪽 버튼 눌림" · "이 영역 다시 그려라"
    해당 핸들러를 부른다            btnExtractDrawingList_Click 같은 것
    핸들러가 끝나면 돌아온다
}
```

**내 핸들러가 도는 동안 루프는 멈춰 있다.** 큐에는 계속 쌓이지만 아무것도 처리되지 않는다.
화면이 안 그려지고, 5초 넘으면 Windows 가 「응답 없음」 딱지를 붙인다.

### `Application.DoEvents()` — 루프를 잠깐 대신 돌린다

```
Application.DoEvents()
  ├ 큐에 쌓인 걸 전부 꺼내 처리
  │    · 그리기 요청 → 화면이 갱신됨
  │    · 클릭       → 그 핸들러가 실행됨      ← 위험한 쪽
  └ 큐가 비면 원래 자리로 돌아온다
```

`Visible = true` 나 `Text = "..."` 는 **「그려달라」고 큐에 넣을 뿐**이다.
`DoEvents` 가 없으면 큐에만 있고 화면은 그대로다.

**위험 — 재진입.** 클릭이 처리된다 = **다른 핸들러가 내 코드 한복판에서 실행된다.**
**같은 스레드**라 끼어든 핸들러가 필드를 마음대로 바꾼다.

지금까지 본 안전장치가 전부 이것 때문이다.

| 장치 | 막는 것 |
|---|---|
| `_p2aInProgress` (`53`) | `DoEvents` 중 일괄 출력이 또 시작되는 것 |
| 버튼 비활성화 (`570`·`572`) | 같은 것의 1차 방어 |
| 취소 체크포인트 21개 | `_cancelRequested` 를 **안전한 자리에서만** 읽기 |
| 모달 차단 (`Clash.cs:1292`) | 끼어든 핸들러가 팝업으로 흐름을 멈추는 것 |

**왜 스레드를 안 나누나** — 이 레포에 `Task.Run` · `new Thread` · `ThreadPool` 이 **0건**이다.
`vizcore3d` 가 화면에 붙은 3D 컨트롤이라 UI 스레드에서만 호출하는 게 원칙이고, 도면 생성이 전부 그 SDK 호출이다.
**스레드를 못 나누니 대신 중간중간 루프를 돌리는** 선택. 대가가 재진입 위험이다.

> 비유 — 혼자 요리하는데 초인종이 울린다. 사람을 더 못 부르니(주방에 나만 들어감)
> **냄비를 불 위에 둔 채 나가서 밀린 손님을 받고 온다.** 그 사이 손님이 주방에 들어와 소금을 넣을 수도 있다.

### 지역 변수를 `try` 밖에 선언하는 이유 (`649~652`)

C# 에서 **변수는 자기가 선언된 중괄호 안에서만 산다.**
`successCount` · `failCount` · `errors` · `totalPdfCount` · `cancelled` 는
**`try/finally` 가 끝난 뒤 `758~773` 에서 결과 팝업을 만들 때 쓴다.**

```csharp
765:  msg = $"...성공: {successCount}개 STRU (PDF {totalPdfCount}개)
실패: {failCount}개";
772:  MessageBox.Show(msg, cancelled ? "취소됨" : "완료", ...);
```

`try` 안에 선언했으면 **컴파일 에러**다. 그래서 `654` 의 `try` 직전에 둔다. 우연이 아니라 필연.

**판단 기준 — 누가 봐야 하는가.** 여러 함수가 보면 필드, 이 함수만 보면 지역 변수.

### `Node.Index` — 모델 전체에 매긴 일련번호

부재가 가진 고유번호가 아니라, **모델을 열 때 SDK 가 트리 전체를 훑으며 0부터 붙이는 통번호**다.

- `GetNodeCount()` = 노드(**Assembly + Part + Body**) 개수
- `GetNodeKind(index)` = **인덱스 하나만 받아** 어셈블리/파트/바디를 답한다 → **번호 공간이 하나**
- 문서 예제가 새 노드 이름을 `"NODE #" + GetNodeCount()` 로 짓는다 → 0부터 이어지는 일련번호

**`Index` 와 `ID` 는 다르다.** 변환 함수가 따로 있다 — `GetNodeId(index)` · `GetNodeIndex(id)`.
문서 예제에서 같은 노드가 `index=10`, `id=4`. 둘 다 `int` 라 **섞어 써도 컴파일러가 안 잡는다.**

> ✅ 우리 코드는 이 함정을 피한다 — `GetNodeId`·`GetNodeIndex`·`GetBodyIndex` 를 **한 번도 안 쓴다.**

**중요한 성질 — 모델이 바뀌면 번호가 무효다.** `Model.Close()` + `Model.Open()`(`BOM.cs:226-230`) 하면 전부 재배치된다.
그래서 사전 초기화 `(8)` 의 캐시 비우기가 있다. 안 비우면 **A 모델의 7번 좌표를 B 모델의 7번 부재 것으로 읽는다** — 조용히 틀린 값.

### `GC.Collect()` 와 파이널라이저 데드락 (`691~698`)

**도면 한 장에 2D 객체가 수천 개.** STRU 마다 쌓이면 메모리가 터지므로 회차마다 청소한다.

**`GC.Collect()` 는 보통 부르면 안 되는 함수**인데 여기선 이유가 있다 — **네이티브 메모리는 GC 눈에 안 보인다.**

```
.NET 힙                  네이티브(C++) 힙
래퍼 객체 40바이트  ──▶   실제 2D 도형 수백 MB
   ↑                          ↑
GC 가 보는 것            GC 가 못 보는 것
```

GC 는 「.NET 힙에 여유 있네」 하고 안 돈다 → 래퍼가 안 수거됨 → 파이널라이저가 안 돎 → **네이티브 메모리가 안 풀린다.**

**빠진 줄 — `GC.WaitForPendingFinalizers()`.** 원래 이 셋이 한 짝이다.
`GC.Collect()` 는 수거 대상을 **파이널라이저 큐에 넣기만** 하고, 실제 정리는 **전용 스레드**가 나중에 한다.

```
UI 스레드                       파이널라이저 스레드
WaitForPendingFinalizers()
   │ 멈춤 ──────────────▶  네이티브 정리 → COM 이라 UI 스레드로 마샬링 시도
   │                          → "UI 스레드야 이것 좀"
   └── 서로 기다린다 = 데드락 ──┘
```

**증상 = 「모델 교체 후 2회차 무한 대기」(이슈 #116).** 2026-08-04 에 **세 곳**에서 뺐다 —
`Stru.cs:692` · `Drawing2D.cs:1106` · `DrawingSheets.cs:1611`.

주석의 *"바로 위 DeleteAll* 이 네이티브 객체를 대량 삭제해 파이널라이저를 쌓아둔 직후라 특히 위험"* —
`694`·`695` 가 방금 수천 개를 큐에 밀어넣은 상태라 **여기가 최악의 자리**였다는 뜻.

**`Thread.Sleep(100)`(`698`) 이 그 빈자리를 메운다.** 끝났는지 확인할 방법이 없으니 시간으로 때운다.
이력: PoC(`9d2b4aa`) `50` → 같은 날 본진(`e15e1e2`) `100`. **올린 사유 기록 없음.**
⚠ 보장이 아니라 희망이다. 다만 부족해도 다음 회차에서 또 정리하니 치명적이진 않다.

## 4단계가 까다로운 이유 — 흐름이 갈라진다

```
DetectClash(864)  ──등록하고 즉시 반환──▶  코드는 다음 줄로
                                              │
        SDK 가 백그라운드에서 간섭검사          │
                    │                          │
                    ▼                          │
   Clash_OnClashTestFinishedEvent              │
        (Clash.cs:1146)                        │
        → 도면 시트를 실제로 만든다             │
        → drawingSheetList 를 채운다            │
                                               ▼
                              878~921  폴링으로 그게 끝나길 기다린다
```

**도면을 만드는 진짜 코드는 이 함수 안에 없다.** 콜백 쪽에 있다.
**이 함수만 읽으면 흐름이 끊긴 것처럼 보인다.**

```csharp
888:  Thread.Sleep(300);                       // SDK 비동기 시작 보장
892:  while (sw.ElapsedMilliseconds < 60000)   // ★ 60초 타임아웃
899:      Thread.Sleep(50);
908:      if (!vizcore3d.Clash.IsBusy && drawingSheetList.Count > 0)
912:          Thread.Sleep(300);               // 콜백 후속 처리 대기
914:          break;
```

**사전 초기화 `(4) drawingSheetList.Clear()` 가 고친 그 버그가 여기다** —
잔재가 있으면 `910` 조건이 영원히 안 맞아 60초를 다 채웠다.
`Sleep` 세 개(`300`·`50`·`300`)는 전부 race 대응이고 주석 `879~887` 에 증상이 적혀 있다.

**실패 대비책**(`871~874`) — `DetectClash` 가 시작조차 못 하면 `GenerateDrawingSheets()` 를 직접 부른다.
