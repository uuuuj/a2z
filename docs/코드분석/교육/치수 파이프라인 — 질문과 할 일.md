### Q1. `descendants` · `allBodies` 는 왜 변수에 담나? 전체 바디 인덱스 뽑고 선택 바디 인덱스 뽑아서 전체 지우고 선택만 표시하면 되는 것 아닌가? (2026-09-01)

**A.** 네 변수 모두 **`837` 이전에 수명이 끝난다.** 그 뒤 200줄에서 하나도 안 쓰인다.

| 변수 | 수명 | 이후 |
|---|---|---|
| `descendants` | `797` → `803` | 없음 |
| `allBodies` | `818` → `821` | 없음 |
| `memberIndices` | `803` → `837` | 없음 |
| `allBodyIndices` | `820` → `837` | 없음 |

**중간 둘을 담는 이유는 있다** —
① `.Where()` 앞에 **null 검사**를 해야 한다 (`801` · `820`).
② `descendants` 는 **에러를 두 단계로 가른다** — `802` "STRU 후손 0건"(후손 자체가 없음) vs
   `808` "STRU 후손 BODY 0건"(후손은 있는데 BODY 가 없음). 합치면 로그로 구분이 안 된다.

**그러나 `allBodyIndices` 는 만들 필요가 없다 — 지적이 맞다.** → 📌 T1

곁가지: `memberIndices` 도 격리에만 쓴다. `CollectBOMData` 에는 `null` 을 넘긴다(`856`).
대상 범위를 **목록이 아니라 화면 가시성으로** 전달하는 구조다.
이유는 `842~843` 주석 — *"xraySelectedNodeIndices 의존은 SDK 상태와 race 가능
(사용자 보고: 첫 클릭 T-023, 재클릭 시 일부만 동작 비결정 동작)"*.
**목록 방식이 비결정 동작을 냈고, 가시성 방식이 사용자가 손으로 하던 패턴과 같아서 그쪽으로 갔다.**

근거: `Form1.Stru.cs:797·801·803·818·820·830·837·855~857`, `Form1.BOM.cs:857~859`

### T1. 가시성 격리를 `Show(Object3DKind.ALL, false)` 한 줄로 바꾼다

**왜** — 전체를 숨기려고 **전체 목록을 만드는 게 낭비**다. SDK 에 「전부 숨겨」 한 줄이 있고,
이 레포가 이미 **10곳**에서 그렇게 쓴다 (`DrawingSheets.cs` 688·893·942·2083·2268·2330·2372·2381,
`MfgDrawing.cs` 1855·2785).

**범위** — `Form1.Stru.cs:818~835` (18줄 → 4줄)

```csharp
// 지금
var allBodies = vizcore3d.Object3D.FromFilter(ALL_INCLUDE_BODY, false);
var allBodyIndices = (allBodies != null)
    ? allBodies.Where(n => n.Kind == NodeKind.BODY).Select(n => n.Index).ToList()
    : new List<int>();
if (allBodyIndices.Count > 0)
{
    vizcore3d.BeginUpdate();
    try { Show(allBodyIndices, false); Show(memberIndices, true); }
    finally { vizcore3d.EndUpdate(); }
}

// 이렇게
vizcore3d.BeginUpdate();
try
{
    vizcore3d.Object3D.Show(VIZCore3D.NET.Data.Object3DKind.ALL, false);
    vizcore3d.Object3D.Show(memberIndices, true);
}
finally { vizcore3d.EndUpdate(); }
```

**얻는 것**
1. 모델 전체 노드 열거가 사라진다 — 지금은 **STRU 마다** `FromFilter`+`Where`+`Select`+`ToList` 가 돈다
2. `if (allBodyIndices.Count > 0)` 가드가 사라진다 — 그게 false 면 **격리가 통째로 스킵**되는 위험 경로였다
3. 레포 관용구와 통일 (`리팩토링 방안.md:317` 과 같은 방향)

⚠ **한 짝으로 고쳐야 한다** — `Object3DKind.ALL` 은 **PART/ASSEMBLY 까지** 숨긴다.
지금은 BODY 만 숨긴다. 최종 복원(`Form1.Stru.cs:716~733`)도 BODY 만 켜므로,
이쪽을 바꾸면 복원도 `Show(Object3DKind.ALL, true)` 로 같이 바꿔야 한다.
(그러면 기존 「PART/ASSEMBLY 미복원」 건도 같이 닫힌다)

**상태: 대기** — 실기 확인 필요 (격리 결과가 도면에 그대로 나오는지)

## 파이프라인 4단계 — 지도

> 상세 추적 진행 중. 확정되는 대로 여기에 채운다.

| 단계 | 무엇 | 중심 메서드 |
|---|---|---|
| **①** 부재 뽑기 | 작업 대상 부재 목록을 만든다 | `CollectBOMData` |
| **②** Osnap 뽑기 | 부재마다 스냅 좌표를 모은다 | `CollectAllOsnap` (`BOM.cs:691`) |
| **③** 간섭검사 | 부재끼리 붙어 있는지 본다 | `DetectClash` → `Clash_OnClashTestFinishedEvent` (`Clash.cs:1146`) |
| **④** 도면 그리기 | 시트를 나누고 2D 로 그린다 | `GenerateDrawingSheets` → `GenerateSheetDrawing2D` |

### 이미 확인된 것

- **③에서 흐름이 갈라진다.** `DetectClash` 는 SDK 에 등록하고 **즉시 반환**한다.
  실제 도면 생성은 `Clash_OnClashTestFinishedEvent`(`Clash.cs:1146`) 콜백에서 이어지고,
  호출자는 `Stru.cs:878~921` 에서 **폴링(최대 60초)** 으로 기다린다.
  → **코드를 위에서 아래로만 읽으면 흐름이 끊긴 것처럼 보인다.**
- **가시성이 작업 범위를 정한다.** `CollectBOMData` 는 「보이는 부재만」 수집한다.
  그래서 `ProcessSingleStruFull` 이 `829/830` 에서 전체를 숨기고 이 STRU 만 켠다.
### 🔴 순서가 생각과 다르다 — **Osnap 은 간섭검사 「뒤」다** (2026-09-01 확인)

말로는 「부재 → Osnap → 간섭검사 → 도면」인데, **코드는 그 순서가 아니다.**

```
① 부재 수집        CollectBOMData
        ↓
③ 간섭검사        DetectClash  ──등록하고 즉시 반환──▶ (호출자는 폴링)
        ↓                                    Stru.cs:878~921
   Clash_OnClashTestFinishedEvent  (Clash.cs:1146)
        ↓  연결성 판정 통과
        ↓  Clash.cs:1308
② Osnap 수집      CompleteMainDimensionPostClash (BOM.cs:545)
        ↓            └ 553  ShowBusyOverlay("Osnap 수집 중...")
        ↓            └ 557  CollectAllOsnap()          ★ 여기가 Osnap
        ↓            └ 563~ 치수 계산
④ 도면 생성        GenerateDrawingSheets
```

**메서드 이름이 그대로 말한다** — `Complete**PostClash**` = 「간섭검사 **이후** 마무리」.

근거:
- `Form1.BOM.cs:552` 주석 `// 1. Osnap 수집` — 이 메서드 안에서 **첫 번째** 단계다
- `Form1.BOM.cs:557` `bool osnapSuccess = CollectAllOsnap();`
- `Form1.Clash.cs:1308` `CompleteMainDimensionPostClash(isSingleMember: false, clashTestCount: testCount);`
- `Form1.BOM.cs:442` 주석 `clashList 수집 → 연결성 판정 → 통과 시 CompleteMainDimensionPostClash 호출`

**예외 하나** — 부재가 하나뿐이면 간섭검사를 건너뛴다.
`Form1.BOM.cs:439` `CompleteMainDimensionPostClash(isSingleMember: true, clashTestCount: 0);`

> ⚠ **리뷰에서 순서를 잘못 말하면 바로 걸린다.** 「부재 → **간섭검사** → Osnap → 도면」이 맞다.

## 직접 확인한 결함 3건

### 🔴 F1. 전부 숨긴 상태로 실행하면 **모델 전량이 대상**이 된다

```csharp
// Form1.BOM.cs:849
return targetNodes.Count > 0 ? targetNodes : allNodes;
```

가시성 모드에서 **보이는 게 0개면 전체 모델을 돌려준다.** `Clash.cs:1050` 에도 같은 폴백이 복제돼 있다.
자동 경로엔 수동에 있는 **5000개 경고 게이트(BOM.cs:392)도 없다.**
⚠ 도입 의도는 주석·커밋에서 찾지 못했다.

### 🔴 F2. `GenerateDrawingSheets` 의 모달에 `_p2aInProgress` 가드가 **없다**

```csharp
// Form1.DrawingSheets.cs:26~30
if (bomList.Count == 0)
{
    MessageBox.Show("BOM 데이터가 없습니다.", ...);   // ← 가드 없음
    return;
}
```

`Clash.cs:1292` 는 `if (!_p2aInProgress)` 로 막아두는데 **여기는 안 막는다.**
자동 일괄 중 이게 뜨면 **폴링 루프의 DoEvents 안에서 모달이 서고**, 사람이 OK 를 누를 때까지
스톱워치가 계속 흘러 결국 60초 타임아웃까지 간다.

### 🔴 F3. 설치도 BFS 가 결과에 기여하지 않는다

```csharp
// Form1.DrawingSheets.cs:125~147   BFS 로 인접 부재를 모으고
// Form1.DrawingSheets.cs:149~152
// BFS에 포함되지 않은 독립 부재도 추가 (Clash가 없는 부재)
foreach (var bom in bomList)
    installMemberIndices.Add(bom.Index);     // ← 조건 없이 전량 추가
```

**BFS 로 무엇을 모으든 그 뒤에 `bomList` 전량을 넣는다.** HashSet 이라 중복은 무시되고
결과는 **항상 전량** — 설치도 `MemberIndices` == 제작도. BFS 는 돌지만 집합을 바꾸지 못한다.

## 리뷰에서 물어볼 만한 것 5개

### Q. `DetectClash` 가 돌려주는 `false` 는 「간섭 없음」인가 「검사 실패」인가?
**둘 다 아니다 — 「등록/시작 실패」다.** `Clash.cs:1115~1117`.
간섭 결과는 이 시점에 **존재조차 하지 않는다.**
그리고 **두 진입점이 다르게 해석한다** — 수동은 단일 부재로 보고 정상 파이프라인을 태우고(`BOM.cs:436`),
자동은 `GenerateDrawingSheets()` 만 직접 부른다(`Stru.cs:876`) → **Osnap 수집을 건너뛴다.**
같은 신호에 한쪽은 4단계, 한쪽은 1단계. 근거 주석이 없다.

### Q. 자동 경로의 60초는 무엇의 시간인가?
**간섭검사만이 아니다.** 종료 조건이 `!Clash.IsBusy && drawingSheetList.Count > 0`(`Stru.cs:915~917`)인데
`drawingSheetList` 는 `CompleteMainDimensionPostClash` **맨 끝**의 `GenerateDrawingSheets()`(`BOM.cs:644`)가 채운다.
그 콜백은 폴링 루프의 `DoEvents`(`Stru.cs:884`)에서 펌핑돼 **같은 스레드·중첩 스택**으로 돈다.
→ **Osnap 전수 수집 · 치수 계산 · 시트 캐시 준비가 전부 그 60초에 들어간다.**
게다가 T-023 연결성 차단(`Clash.cs:1284~1305`)에 걸려도 시트가 안 차서 **같은 타임아웃으로 보고된다** —
「부재가 안 붙어 있다」가 「타임아웃」으로 둔갑한다.

### Q. ①의 대상과 ③의 대상이 같다고 보장되나?
**보장 안 된다.** ③은 `GetBOMTargetNodes` 를 안 부르고 `Clash.cs:1029~1051` 에 **인라인 복제**했는데,
selectedSet 분기에 **`bodyToPartIndexMap` 부모-Part 폴백(`BOM.cs:834~835`)이 빠져 있다.**
지금 사고가 안 나는 건 두 진입점이 직전에 `xraySelectedNodeIndices.Clear()` 를 하기 때문뿐이고,
**그 규약을 어기는 경로가 이미 하나 있다** — `btnCollectBOM_Click`(`BOM.cs:1083`)은 Clear 를 안 한다.

### Q. 부재 N개면 검사가 몇 건인가?

`GroupA=전체, GroupB=후보 전체` 로 **1건**(`Clash.cs:1102~1103`) 처리한다.
SDK 가 그룹 검사에서 모든 내부 쌍을 돌려주는지는 PDB 가 없어 확인 못 함(추정).

## ❓ Q2. 노드를 거치지 말고 바로 인덱스로 바꾸면 되지 않나?

**A. 순서는 강제다.** `GetChildObject3d` 는 `List<Node>` 만 돌려주고,
`Kind == BODY` 필터를 하려면 **Node 가 있어야 한다**(`Kind` 는 Node 의 속성).
「노드 받기 → Kind 로 거르기 → Index 뽑기」 말고 다른 길이 없다.

**중간 변수를 없앨 수는 있다** — 한 줄 체인으로 쓰면 된다.
대신 **에러 2단계 구분을 잃는다**: `802` "STRU 후손 0건"(후손 자체가 없음) vs
`808` "STRU 후손 BODY 0건"(후손은 있는데 BODY 가 없음). 그 문구가 `errors` 에 담겨 결과 팝업에 뜬다.

**전체 부재 쪽(`818~822`)은 얘기가 다르다 — 애초에 목록이 필요 없다.** → 📌 T1

## ❓ Q3. `836` 의 `Application.DoEvents` 는 필요한가?

**A. 화면 갱신용으로 보이나 단정 못 한다.**

## ❓ Q4. 가시성 격리는 필수인가? 꼭 띄워야 하나?

**A. 지금 구조에선 필수다 — 범위를 전달하는 유일한 수단이라서.**
`855` 가 `CollectBOMData(null, ...)` 이라 목록을 안 넘긴다.

**그런데 목록으로 넘기는 길이 이미 있다 — 수동 경로가 그렇게 한다.**

자동 경로도 `descendants.Where(Kind == BODY).ToList()` 를 넘길 수 있다 — **`descendants` 가 이미 손에 있다.**

⚠ **단 격리는 2D 렌더링에도 걸린다.** 은선투영이 보이는 것만 그린다.
다만 `ApplySheetSelection`(`DrawingSheets.cs:651`)이 **시트마다 다시 격리**하므로,
여기 격리가 렌더링에 꼭 필요한지는 **확인이 필요하다**. → 📌 T4

## ❓ Q5. `xraySelectedNodeIndices.Clear()` 는 필수인가? Body 인덱스가 있는데?

**A. 필수다. 그리고 방향이 반대다 — 「비우는 것」이 스위치다.**

`GetBOMTargetNodes`(`BOM.cs:817~840`)는 **두 모드**로 갈린다.

```csharp

    ? new HashSet<int>(xraySelectedNodeIndices)
    : null;
...
```

| xray 상태 | 무엇으로 거르나 |
|---|---|
