## Visual Studio 글자 색깔 — 무슨 뜻인가

VS 어두운 테마 기본값이다. **색 = 그 단어의 "신분"** 이다.

| 색 | 신분 | 예시 | 한 줄 설명 |
|---|---|---|---|
| 🔵 **파란색** | **키워드** | `private` `void` `new` `if` `null` `false` `return` `class` `string` `int` `bool` | C# 언어가 미리 정해둔 단어. 내가 이름으로 못 쓴다 |
| 🟢 **청록/연두** | **타입(클래스·구조체)** | `Panel` `Color` `Label` `Button` `Font` `Size` `Point` `DockStyle` `VIZCore3DControl` | "무엇의 종류". 설계도 이름 |
| 🟡 **노란색** | **메서드(함수)** | `ShowBusyOverlay` `FromArgb` `Add` `Run` `Open` | 부르면 뭔가 하는 것. 뒤에 `( )` 가 붙는다 |
| 🩵 **하늘색** | **변수·필드·파라미터·enum 값** | `message` `busyOverlay` `vizcore3d` `Fill` | 값이 담기는 그릇 |
| ⚪ **흰색/회색** | **속성(프로퍼티)** | `BackColor` `Visible` `Dock` `Controls` `Text` | 그 물건의 성질. `.` 뒤에 오고 `( )` 가 없다 |
| 🟠 **주황/연어색** | **문자열 값** | `"처리 중..."` `"맑은 고딕"` | 따옴표 안의 실제 글자 |
| 🟩 **초록색** | **주석** | `// 이렇게` `/// <summary>` | 사람이 읽는 설명. 실행 안 됨 |

### 헷갈리는 지점 — `string`은 왜 파란색인가

사용자가 `string`·`Color`·`Panel`을 **같은 무리로 봤는데, 그 직관이 맞다.** 셋 다 **타입**이다.
그런데 `string`만 파란색인 건 C#이 `System.String`을 `string`이라는 **키워드 별칭**으로도 쓰게 해줬기 때문이다.
`int`(=`System.Int32`)·`bool`(=`System.Boolean`)도 마찬가지. **의미는 타입, 색은 키워드.**

### 구분 요령 — `( )` 유무

```csharp
busyOverlay.Visible = false;        // ⚪ Visible — 괄호 없음 → 속성 (성질)
busyOverlay.Controls.Add(label);    // 🟡 Add     — 괄호 있음 → 메서드 (동작)
```

## 사용자 질문 기록

### Q. 「필드」가 뭐야?

**클래스가 들고 다니는 변수.** 메서드 안에서만 살다 사라지는 변수(지역 변수)와 달리,
**객체가 살아 있는 내내 남아 있고, 그 클래스의 모든 메서드가 같이 읽고 쓴다.**

```csharp
public partial class Form1
{
    private float _lastModelShiftCanvasX = 0f;   // ← 필드. Form1이 켜져 있는 내내 존재

    private void ShowAllDimensions()
    {
        float baseOffset;                        // ← 지역 변수. 이 함수 끝나면 사라짐
        _lastModelShiftCanvasX = 12.5f;          //   필드는 여기서 써도 다른 함수가 읽는다
    }
}
```

📌 **이 프로그램의 핵심 문제가 여기 있다.** `Form1`은 파일 12개로 나뉘어 있지만 **클래스는 하나**라
필드 **96개**를 12개 파일이 공유한다. 그래서 "파일 열기" 할 때 **23줄을 손으로 `.Clear()`** 해야 한다
(→ [2교시](./2교시%20—%20모델%20열기.md) ②). 리팩토링 「공유 상태 묶기」가 이걸 손보는 것이다.

### Q. 「DataGridView」가 뭐야?

**윈도우 화면에 표(격자)를 그려주는 부품.** 엑셀 시트처럼 행·열이 있다.
`Form1` 생성자의 `SetupAttributeColumns()`가 이 표의 컬럼을 만든다.

이 프로그램의 화면 부품(컨트롤) 종류:

| 부품 | 화면에서 | 코드 이름 예 |
|---|---|---|
| `Button` | 누르는 버튼 | `btnOpen` (「파일 열기」) |
| `ListView` | 목록 (여러 컬럼) | `lvBOM` `lvClash` `lvDimension` |
| `DataGridView` | 표 (편집 가능한 격자) | 부재 정보 탭 |
| `CheckedListBox` | 체크박스 달린 목록 | `clbStruList` (STRU 목록) |
| `Panel` | 다른 부품을 담는 빈 상자 | `panelViewer` (3D 뷰어가 여기 들어감) |
| `Label` | 그냥 글자 | `lblStruTitle` |
| `TextBox` | 입력창 | `txtStruSearch` |

**이름 앞머리로 종류를 안다** — `btn`=버튼, `lv`=ListView, `clb`=CheckedListBox, `lbl`=Label, `txt`=TextBox, `panel`=Panel.

### Q. `busyOverlayCancelButton.Click` — 「Click」은 이벤트인가?

**맞다. 이벤트다.**

```csharp
busyOverlayCancelButton.Click += BusyOverlayCancelButton_Click;
//                       ↑ 이벤트          ↑ 이벤트가 나면 부를 함수
//                          ↑ += "이 함수도 불러줘" 라고 등록
```

**이벤트 = 벨.** "이런 일이 생기면 알려줘"를 등록해두는 자리다. `+=` 는 등록이지 실행이 아니다.
버튼을 누르는 순간 윈도우가 `Click` 이벤트를 울리고, 등록된 함수가 그때 실행된다.

📌 [1교시](./1교시%20—%20켜지는%20순간.md)의 **벨①**(`OnInitializedVIZCore3D`)·**벨②**(`OnClashTestFinishedEvent`)가
정확히 같은 물건이다. 버튼 클릭이든 SDK 준비 완료든 **전부 이벤트**다.

### Q. `VIZCore3D.NET` 이런 건 뭐야?

**네임스페이스(namespace)** — 이름이 겹치지 않게 묶어둔 **폴더** 같은 것이다.

```csharp
VIZCore3D.NET.ModuleInitializer.Run();
└─────┬─────┘ └───────┬───────┘ └┬┘
  네임스페이스        클래스     메서드
   (폴더 경로)       (설계도)    (동작)
```

`.`으로 파고들어 간다. 폴더 경로 `C:\문서\보고서.docx`와 같은 구조다.

파일 맨 위 `using System.Windows.Forms;` 는 **"이 폴더는 매번 안 쓰고 생략하겠다"** 는 선언이다.
그래서 `System.Windows.Forms.Panel` 을 그냥 `Panel` 로 쓸 수 있다.

### Q. 「부모」가 뭔데?

**나를 담고 있는 상자.** `A.Controls.Add(B)` 를 하는 순간 **A가 부모, B가 자식**이 된다.

```csharp
panelViewer.Controls.Add(vizcore3d);
//    ↑ 부모              ↑ 자식
```

`Controls` = "내가 품은 자식 목록", `Add` = 거기 하나 넣기.
**부모는 코드가 정한다.** `Controls.Add` 한 줄을 찾으면 부모가 누군지 알 수 있다.

#### 이 프로그램의 실제 화면 나무

`Form1.Designer.cs`의 `Controls.Add` 를 전부 뽑으면 이렇게 된다:


#### 그래서 Dock이 무슨 뜻이 되나

**"내 부모가 준 공간 안에서 나는 어디에 붙을까".** 같은 부모(`tabPageDrawing`) 안의 세 자식:

| `panelDrawingHeader` | `Top` | **위에** 가로로 쫙 (제목 줄) |
| `panelDrawingButtons` | `Bottom` | **아래에** 가로로 쫙 (버튼 7개) |

그래서 화면이 「제목 / 목록 / 버튼」 세 줄로 나뉜다.

순으로 전부 따라 커진다. **각 부품은 자기 부모만 신경 쓰면 된다.**

`Form1.Designer.cs`에서 **`Controls.Add`** 검색 → 30줄 넘게 나온다. **그 목록이 곧 화면 구조도다.**
`왼쪽.Controls.Add(오른쪽)` 을 "왼쪽이 오른쪽을 품는다"로 읽으면 위 나무가 그대로 나온다.

`panelDrawingButtons`의 자식이고 그건 `Dock=Bottom`이니 **「도면」 탭 맨 아래 버튼 줄**에 있다.

### Q. `sender`와 `e`는 뭘 하나? 이름을 바꿔도 되나? 어떻게 알고 쓰나?

**둘 다 "윈도우/SDK가 핸들러에게 건네주는 정보"** 다.

| | 무엇 | 이 프로그램에서 (2026-08-24 실측) |
|---|---|---|
| `sender` | **누가 일으켰나** | **0회 사용** — 버튼마다 핸들러가 따로라 구분할 필요가 없다 |
| `e` | **무슨 일이 났나** (상세) | **4곳 사용** — 여기선 없으면 동작이 불가능하다 |

#### `e`를 실제로 쓰는 4곳 — 전부 "정보가 딸려 오는 이벤트"

```csharp
// ① 간섭검사 완료 — 어느 검사가 끝났나  (Form1.Clash.cs:1146)  ★ 벨②
private void Clash_OnClashTestFinishedEvent(object sender, ClashEventArgs e)
{
    if (!AdvanceSilentClashSequence(e.ID)) return;   // e.ID = 끝난 검사 번호
}
```
검사를 여러 개 걸어놓고 순서대로 도는데, **`e.ID`가 없으면 "지금 끝난 게 어느 검사인지" 알 수 없다.**

```csharp
// ② Osnap 점을 찾음  (Form1.Drawing2D.cs:706)
private void GeometryUtility_OnOsnapPickingItem(object sender, OsnapPickingItemEventArgs e)
{
    if (e.Point == null) return;                      // e.Point = 찾은 점
    var point = new Vertex3D(e.Point.X, e.Point.Y, e.Point.Z);
}

// ③ STRU 체크박스 토글  (Form1.Stru.cs:362)
private void ClbStruList_ItemCheck(object sender, ItemCheckEventArgs e)
{
    if (e.Index < 0 || ...) return;                   // e.Index = 몇 번째
    if (e.NewValue == CheckState.Checked) futureCheckedIdx.Add(e.Index);   // e.NewValue = 켜는 중?
    else futureCheckedIdx.Remove(e.Index);
}
```
📌 주석이 이유를 밝힌다 — `// ItemCheck는 체크 *직전* — e.NewValue로 미래 체크 set 계산`.
**체크가 바뀌기 전에 울리는 이벤트**라 목록을 읽으면 아직 옛 상태다. `e.NewValue`로 "바뀔 값"을 받아야 정확하다.

#### `e`의 타입이 이벤트마다 다르다

| 핸들러 | `e`의 타입 | 담긴 정보 |
|---|---|---|
| 버튼 `Click` 49개 | `EventArgs` | **빈 껍데기** |
| `ClbStruList_ItemCheck` | `ItemCheckEventArgs` | `Index` `NewValue` `CurrentValue` |
| `Clash_OnClashTestFinishedEvent` | `ClashEventArgs` | `ID` |
| `GeometryUtility_OnOsnapPickingItem` | `OsnapPickingItemEventArgs` | `Point` |
| `Object3D_OnObject3DSelected` | `Object3DSelectedEventArgs` | 선택 노드 정보 |

📌 **읽는 요령**: `EventArgs`가 그대로면 **정보 없는 이벤트**(무시해도 됨),
**뒤에 뭐가 붙어 있으면 정보가 있으니 봐야 한다.**

#### 이름은 바꿔도 된다 / 타입·개수는 못 바꾼다

```csharp
private void btnOpen_Click(object 보낸놈, EventArgs 정보)   // ✅ 동작한다
private void btnOpen_Click(object s, EventArgs args)        // ✅ 동작한다

private void btnOpen_Click()                                // ❌ 컴파일 에러
private void btnOpen_Click(EventArgs e)                     // ❌ 컴파일 에러
private void btnOpen_Click(string sender, int e)            // ❌ 컴파일 에러
```

`sender`·`e`는 **관례**일 뿐이다. 세계 공통이라 남이 알아보기 좋아서 따른다.

**모양이 고정인 이유 — 델리게이트(delegate)**

```csharp
// .NET이 미리 정해둔 것
public delegate void EventHandler(object sender, EventArgs e);
//                                └──── 이 모양이어야만 += 로 연결된다 ────┘
```

**델리게이트 = "함수의 모양을 미리 정해둔 것".** `+=` 우변 함수는 반드시 이 모양이어야 하고,
아니면 컴파일러가 막는다. Designer 코드에 그게 드러나 있다:

```csharp
this.btnOpen.Click += new System.EventHandler(this.btnOpen_Click);
//                        └── 이 모양이 맞는지 확인해줘
this.clbStruList.ItemCheck += new ItemCheckEventHandler(this.ClbStruList_ItemCheck);
//                                └── ItemCheck는 다른 델리게이트 = 다른 모양
```

**이벤트마다 정해진 델리게이트가 다르고, 그게 `e`의 타입을 결정한다.**

#### 실제로는 Visual Studio가 만들어준다

| 방법 | 조작 |
|---|---|
| **디자이너에서 더블클릭** | 버튼 더블클릭 → 핸들러 자동 생성 + 배선까지 |
| **속성 창** | 부품 선택 → 번개 아이콘(⚡) → 이벤트 목록에서 더블클릭 |
| **`+=` 치고 Tab Tab** | `btnOpen.Click +=` 까지 치면 VS가 모양을 맞춰 껍데기 생성 |

📌 **모양을 외울 부담이 없다.** VS가 델리게이트를 보고 맞는 모양을 써준다.
`btnOpen_Click` 같은 이름도 VS 자동 생성 규칙이다.

| 질문 | 답 |
|---|---|
| 기본 문법인가? | 문법보단 **약속(델리게이트)**. `EventHandler`가 정한 모양 |
| 다른 문자 써도 되나? | **이름은 자유. 타입·개수는 고정** |
| 어떻게 아나? | **VS가 만들어준다** (더블클릭 / `+=` 뒤 Tab Tab) |
| 안 쓸 거면? | **그래도 받아야 한다.** 모양이 안 맞으면 연결이 안 됨 |

### Q. 「이벤트 핸들러」가 뭔데? / Q. 그거 찾는 것부터가 코드분석의 시작인가?

#### 프로그램은 위에서 아래로 흐르지 않는다

콘솔 프로그램은 코드가 쭉 흐르지만, **화면이 있는 프로그램은 그냥 기다린다.**

```
프로그램 켜짐 → 준비 끝 → ⏸ 아무것도 안 하고 기다림
                              ↑
                    사용자가 버튼을 누름 → 그때만 코드가 돈다 → 다시 ⏸
```

[1교시](./1교시%20—%20켜지는%20순간.md)의 `Application.Run(new Form1())` 이 이 **"기다림"** 이다.
그 안에서 윈도우가 무한 반복하며 "마우스 눌렸나? 키 눌렸나?"를 감시한다.

#### 그래서 세 조각이 필요하다

| 조각 | 이름 | 예 |
|---|---|---|
| ① **사건** | 이벤트 | `Click` (버튼이 눌림) |
| ② **등록** | `+=` | `btnOpen.Click += btnOpen_Click;` |
| ③ **반응할 함수** | **이벤트 핸들러** | `private void btnOpen_Click(object sender, EventArgs e)` |

**이벤트 핸들러 = "그 사건이 나면 실행될 함수".** 이벤트(event)를 처리(handle)하는 자(er).

문법적으로는 **보통 메서드와 똑같다.** 다른 건 둘뿐:
① 모양 고정 `(object sender, EventArgs e)` ② **아무도 직접 안 부름** — `+=` 등록만, 부르는 건 윈도우/SDK

### Q. `btnOpen_Click` 은 Designer에만 참조가 있는데, 이벤트라서 그런가?

**맞다.** 이벤트 핸들러라서 그렇다.

```csharp
this.btnOpen.Click += new System.EventHandler(this.btnOpen_Click);
//   Form1.Designer.cs:1202 — 이 한 줄이 유일한 "참조"
```

**부르는 게 아니라 등록하는 것이다.** `+=`로 "이 함수를 기억해둬"라고만 한다.
실제로 부르는 건 **윈도우(런타임)** — 사용자가 버튼을 누르는 순간에.

| | 일반 메서드 | 이벤트 핸들러 |
|---|---|---|
| 누가 부르나 | **다른 코드가** `이름()` 으로 | **윈도우가** 사건이 났을 때 |
| 코드에 보이는 참조 | 부르는 곳마다 (여러 개) | **등록한 `+=` 한 줄뿐** |
| 예 | `BuildBodyToPartNameMap()` — 2곳 호출 | `btnOpen_Click` — 배선 1줄, 호출 0 |

📌 `Shift+F12` 결과가 **`Designer.cs`의 `+=` 한 줄만** 나오는 게 정상이다.

#### 이름이 `_Click`인 건 관례일 뿐

**이름 때문에 연결되는 게 아니라 오직 `+=` 줄이 연결한다.**
`버튼이름_이벤트이름` 은 Visual Studio가 자동으로 지어주는 이름 규칙이다.

#### 모양이 정해져 있다

```csharp
private void btnOpen_Click(object sender, EventArgs e)
//                         └────┬────┘  └────┬───┘
//                     누가 일으켰나?    딸린 정보
```

파라미터 2개가 **고정**이다. 바꾸면 `+=`가 안 된다.

- **`sender`** — 사건을 일으킨 물건(여기선 `btnOpen` 자신). 버튼 여러 개가 **같은 핸들러**를 공유할 때 구분용
- **`e`** — 딸린 정보. 클릭은 정보가 없어 빈 `EventArgs`지만, 마우스 이벤트면 `MouseEventArgs`에 좌표가 들어 있다

`btnOpen_Click`은 둘 다 안 쓴다 — 그래도 **모양은 맞춰야** 해서 받아만 둔다.
(⚠ 버튼 `Click`은 그렇지만 **SDK 이벤트·ItemCheck는 `e`를 실제로 쓴다** — 위 절 참조.)

#### 🔑 여기서 죽은 코드가 나왔다

실측: 핸들러 선언 **36개** / Designer 배선 **37개** (일부는 같은 핸들러 공유) — 지금은 맞다.
그런데 **삭제 전에는 핸들러가 44개**였다.

`btnShowAxisX/Y/Z_Click` · `btnShowISO_Click` · `btnDrawingISO/AxisX/AxisY/AxisZ_Click`
— 이 **8개는 `+=` 줄이 어디에도 없었다.**

> **이벤트 핸들러는 `+=` 없이는 절대 실행되지 않는다.**
> 함수는 멀쩡히 컴파일되고 코드도 그럴듯한데 **아무도 등록하지 않아 영원히 안 불리는** 상태였다.
> 화면의 축·ISO 버튼은 실제로는 `GlobalViews` 쪽에 배선돼 있었다.

아무 `_Click`에 `Shift+F12` → **반드시 `Designer.cs`의 `+=` 줄이 나와야 한다.** 안 나오면 죽은 코드.

### Q. Dock이 뭐야?

**부모 상자의 「어느 벽에 붙을까」.** 부품 위치를 정하는 방법은 둘이다.

| 방법 | 어떻게 | 창 크기가 바뀌면 |
|---|---|---|
| **좌표로** (`Dock=None`) | "왼쪽 11px, 위 5px, 크기 211×50" | **안 따라간다.** 그 자리 그대로 |
| **Dock으로** | "위쪽 벽에 붙어" | **자동으로 따라간다** |

Dock은 후자다. **좌표를 안 쓰고 "어느 벽"만 말한다.**

| 값 | 결과 |
|---|---|
| `Top` / `Bottom` | 위/아래에 **가로로 쫙**. 높이만 내가 정하고 너비는 부모에 맞춰짐 |
| `Left` / `Right` | 좌/우에 **세로로 쫙**. 너비만 내가 정하고 높이가 맞춰짐 |
| **`Fill`** | **남은 공간 전부.** 너비·높이 둘 다 부모가 정함 |
| `None` | 좌표·크기 그대로 (기본값) |

#### 🔑 순서가 중요하다 — 먼저 붙는 쪽이 먼저 먹는다

「도면」 탭이 실제 예다. 같은 부모에 셋이 들어 있다:

```csharp
tabPageDrawing.Controls.Add(splitContainerDrawing);   // Fill
tabPageDrawing.Controls.Add(panelDrawingButtons);     // Bottom
tabPageDrawing.Controls.Add(panelDrawingHeader);      // Top
```

```
┌──────────────────────────────┐
│ panelDrawingHeader   Top     │ ← ① 위쪽 몫을 떼감
├──────────────────────────────┤
│ splitContainerDrawing        │ ← ③ 남은 걸 전부 (Fill)
│   (도면 목록 · BOM 표)        │
├──────────────────────────────┤
│ panelDrawingButtons  Bottom  │ ← ② 아래쪽 몫을 떼감
│ [제작도][조립도][설치도]…      │
└──────────────────────────────┘
```

📌 **`Top`·`Bottom`이 먼저 몫을 가져가고 `Fill`은 남은 것만 받는다.**
그래서 창을 위아래로 늘리면 **제목·버튼 줄은 그대로이고 가운데 목록만 커진다.**

### Q. `DockStyle.Fill` 은? / Q. enum이 뭔데?

**enum = 정해진 선택지 목록.** "이 자리에 올 수 있는 값은 이것들뿐"이라고 못박는 것.

```csharp
vizcore3d.Dock = DockStyle.Fill;
//               └───┬───┘ └┬┘
//            enum 이름(🟢타입) 그중 한 값(🩵)
```

`DockStyle`의 선택지: `None` `Top` `Bottom` `Left` `Right` `Fill`.
`Fill` = "부모가 준 공간을 꽉 채워라" → 3D 뷰어가 `panelViewer` 크기에 딱 맞게 늘어난다.

#### 이 프로젝트가 직접 만든 enum — `Form1.DrawingSheets.cs:1251`

```csharp

    Installation     // 설치도
```

**왜 만들었나 — 버튼 3개가 같은 함수를 쓰려고.**

| **의미** | `Fabrication` — 읽으면 안다 | `-1` — 뭔지 알 수 없다 |

```csharp
    switch (exportKind)
    {
        case DrawingSheetExportKind.Fabrication:  return sheet.BaseMemberIndex == -1;
        case DrawingSheetExportKind.Assembly:     return sheet.BaseMemberIndex >= 0;
        case DrawingSheetExportKind.Installation: return sheet.BaseMemberIndex == -2;
    }
}
```

**왼쪽은 enum, 오른쪽은 맨숫자다.** `BaseMemberIndex`가
`-1`=제작도 · `-2`=설치도 · `0 이상`=조립도(그 값이 기준 부재 번호)라는 **약속이 코드에 못박혀 있지 않다.**
이걸 **매직 넘버**라 한다. `-2`를 처음 본 사람은 뜻을 알 수 없고, `-3`을 넣어도 컴파일러가 안 막는다.

> 📌 **enum이 왜 좋은지 알려면 enum을 안 쓴 코드를 보면 되는데, 그게 같은 함수 안에 나란히 있다.**
> 리팩토링에서 손볼 지점.

#### 자주 보이는 enum

| 값 | 어디서 |
|---|---|
| `DockStyle.Fill` | 부품을 부모 공간에 꽉 채우기 |
| `DialogResult.OK` | 파일 선택창에서 확인을 눌렀나 |
| `Object3dFilter.ASSEMBLY` | 나무에서 어셈블리만 골라내기 |

| `MessageBoxIcon.Error` | 오류 창의 빨간 아이콘 |

**앞이 enum 이름(🟢타입), 뒤가 그중 한 값(🩵).** 위 색깔 표와 그대로 이어진다.

### Q. `new VIZCore3DControl()` — 메서드는 아닌 것 같은데?

**생성자(constructor) 호출이다.** `new 타입이름()` = **"이 설계도로 물건을 하나 만들어라".**

📌 **1교시에서 이미 봤다.** `Program.cs`의 `Application.Run(new Form1());` —
`new Form1()`이 바로 이것이다. **창(Form1)을 하나 만들어라.** 만드는 순간 `public Form1() { ... }` 생성자가 실행된다.

`VIZCore3DControl`도 똑같이 만들어지고, 만들어진 물건을 `vizcore3d` **필드**에 담아두기 때문에

### Q. `partial`이 뭐야? 13개 파일인데 왜 클래스가 하나야?

### Q. `private` / `internal` / `public` — 뭘 써야 해?

**원칙은 "무조건 private"이 아니라 "쓰는 만큼만 연다".**

**클래스를 갈라야 비로소 `private`이 일을 시작한다.**

📌 **이 프로젝트는 프로젝트가 하나뿐**(`A2Z.csproj` → `A2Z.exe`)이라
`public`과 `internal`이 실질적으로 같다. **`internal`이 더 정확한 표현.**

### Q. `partial`에서 `Form1`이 `Form`을 호출하는 거야?

**아니다. `partial` 과 `: Form` 은 서로 무관한 별개다.**

```csharp
// Form1.cs:16 — 13개 파일 중 여기 한 곳에만 ': Form' 이 붙어 있다
public partial class Form1 : Form

// 나머지 12개 파일 — 상속 표시 없음
public partial class Form1        // Form1.BOM.cs:11
public partial class Form1        // Form1.Clash.cs:10
```

- **`: Form`** = 「나는 `Form`의 **일종이다**」 — 관계가 *~이다*. 괄호가 없다
- **`partial`** = 「이 클래스는 **여러 파일에 나눠 적혀 있다**」 — 컴파일하면 하나로 합쳐진다
- **호출**은 괄호가 붙는 것 — `Model.Open(path)` · `btnOpen_Click()`. 관계가 *~를 시킨다*

상속 표시는 **조각 중 한 곳에만** 쓰면 된다. 그래서 나머지 12개 파일이 `: Form` 없이도
같은 클래스이고, 합쳐진 뒤에는 어느 파일에 있든 전부 `Form`의 기능을 쓴다.

**진짜로 부모를 부르는 코드는 따로 있다** — `Form1.Designer.cs:19`:

```csharp
protected override void Dispose(bool disposing)
{
    if (disposing && (components != null)) components.Dispose();
    base.Dispose(disposing);   // ← 여기. base = 부모(Form)
}
```

`override` = 「물려받은 걸 내 식으로 덮어쓴다」 · `base.` = 「그래도 부모가 하던 일은 마저 시킨다」.
우리 것(`components`)만 정리하고 나머지 창 정리는 `Form`에게 맡긴다.


> ⚠ DLL 두 개(222MB·88MB)는 GitHub 100MB 한도를 넘어 레포에 못 넣는다.
> `.gitignore` 로 빼고 각 PC가 `lib\` 에 직접 둔다 — **클론만 해서는 빌드가 안 된다.**

### Q. `void`·`bool` 도 클래스야?

**아니다.** 반환형 자리에 오는 건 **타입**이고, 타입에는 종류가 있다.

| | 무엇 | 예 |
|---|---|---|
| **class** | 참조 타입 | `string` `List<>` `BOMData` `MfgViewPose` |
| **struct** | 값 타입 | `int` `bool` `float` **`MfgAxisVector`** `BodyBoundsData` |
| **enum** | 정해진 선택지 | `DrawingSheetExportKind` `DockStyle` |
| **`void`** | **타입이 아님** | "돌려줄 게 없다" |

🔑 **class와 struct의 실제 차이 — 복사냐 공유냐**

```csharp
MfgAxisVector b = a;   // struct: 값이 통째로 복사됨 (별개 물건 둘)
MfgViewPose p2 = p1;   // class:  주소만 복사 (같은 물건 하나)
```

📌 **`bomList`를 여러 파일이 만지면 다 같은 목록인 이유**가 `List<>`가 class(참조 타입)라서다.

### Q. `private MfgViewPose BuildMfgSceneCore(...)` — MfgViewPose가 뭐야?

**반환형(돌려주는 것의 종류)이지 소속이 아니다.**

```csharp
private  MfgViewPose  BuildMfgSceneCore(int bomIndex, bool reserve = false)
   ↑          ↑              ↑                    ↑
접근제한자  반환형(타입)      메서드 이름            파라미터
```

`void`·`bool`·`string` 자리에 `MfgViewPose`가 들어간 것뿐이다.
**`BuildMfgSceneCore`는 `Form1`의 메서드**이고, `MfgViewPose`는 `Models/MfgViewPose.cs`의 별개 클래스다.

⚠ **클래스를 반환하는 게 아니라 「클래스로 만든 객체」를 반환한다.** 설계도는 파일에 그대로 있다.

### Q. 프로젝트가 뭐야? 여러 개로 나눌 수 있어?

**프로젝트 = `.csproj` 하나 = 컴파일 단위 = 결과물 하나.**

```
A2Z.sln              솔루션 (프로젝트들의 묶음)
  └ A2Z/A2Z.csproj   프로젝트 — 이 솔루션엔 하나뿐
       ↓ 컴파일
     A2Z.exe
```

**여러 개로 나누는 이유 3가지**: 테스트 분리 · 재사용 · **경계 강제**
(`Core.dll`이 UI를 **참조하지 못하게** 컴파일러가 막는다).

🔴 **a2z는 지금 나눠도 실익이 없다** (2026-08-31 실측):

| 분류 | 메서드 | 줄 | 비율 |
|---|---|---|---|
| SDK 직접 사용 | 171 | **11,975** | **81%** |
| UI 직접 사용 | 45 | 1,002 | 7% |
| **둘 다 안 씀 (순수 계산)** | **98** | **1,758** | **12%** |

**81%가 SDK를 직접 만져서** `Core.dll`을 만들어도 거기서도 SDK를 참조해야 한다.
**STEP 3(계산 분리)로 순수 코드 비율을 올린 뒤**가 맞다.

### Q. 테스트 프로젝트가 뭐야? git이랑 뭐가 달라?

```
git    ──  시간 축   ──  "무엇이 언제 바뀌었나 · 되돌릴 수 있나"
테스트  ──  정확성 축 ──  "지금 이 코드가 맞게 동작하나"
```

🔑 **git은 「되돌릴 수 있게」 해주고, 테스트는 「되돌려야 한다는 걸 알게」 해준다.**
**둘 다 필요하고 서로 못 한다.** git만 있으면 **뭘 되돌려야 하는지 모른다** ← 지금 상태.

**층으로 보면:**
```
① 빌드    문법이 맞나           ← 이미 있음
② 테스트  계산이 맞나           ← 없음  ★ 빈 층
③ 실기    도면이 제대로 나오나   ← 사람이 함 (②의 몫까지 떠맡는 중)
④ git     기록 · 되돌리기       ← 이미 있음
```

**정답은 내가 넣어야 한다.** 다만 **리팩토링에서는 「지금 나오는 값」이 정답**이라
알아낼 필요 없이 박제만 하면 된다 (characterization test).

⚠ 테스트는 **12%만 커버**한다. SDK가 그리는 도면은 여전히 실기로만 확인 가능.

### Q. 폴더들은 뭐야?

| 폴더 | 무엇 | git |
|---|---|---|
| `bin/` | **빌드 결과물** — `A2Z.exe` · DLL · 복사된 리소스 | ❌ |
| `obj/` | 빌드 중간 산물 | ❌ |
| `Properties/` | `AssemblyInfo.cs`(버전) · `Resources.resx` · `Settings` | ✅ |
| `Models/` | 데이터 클래스 — 지금은 `MfgViewPose.cs` 하나 | ✅ |
| `templates/` | **소스에선 빈 폴더**, 빌드하면 엑셀 2개가 복사됨 | ✅ |

📌 `Models/` 폴더가 있는데 `Models.cs`는 밖에 있다 — 정리 대상.
📌 `templates/` 원본 엑셀은 **레포 루트**에 있고 `csproj`가 복사한다.
`csproj`의 `<Link>templates\...</Link>` 와 코드의 `TemplateOutputFolderName` 이 **문자열로 묶여 있어** 한쪽만 바꾸면 깨진다.

### Q. `A2Z.csproj` 는 뭐야?

**빌드 설명서.** *"이 프로젝트를 어떻게 컴파일할지"* 를 적은 XML.

```xml
<OutputType>WinExe</OutputType>              창 있는 프로그램으로
<TargetFrameworkVersion>v4.8</...>           .NET Framework 4.8
<Compile Include="Form1.cs" />               이 파일들을 컴파일
<Reference Include="VIZCore3D+.NET">         이 DLL을 참조
<Content Include="..\제작도_도면.xlsx">      이 파일을 실행 폴더로 복사
```

### Q. 「무창」·「어댑터」·「참조축 정렬」이 뭐야?

| 말 | 출처 | 뜻 |
|---|---|---|
| **무창(silent)** | 원본 코드 | **SDK 진행창을 끔** (`PerformInterferenceCheck(id, progressForm: false)`) — 우리 진행창과 겹쳐서 |
| **어댑터** | 원본 코드 | 같은 결과(`MfgViewPose`)를 **목적지에 맞게 내보내는 쪽** — 미리보기 / PDF |
| **참조축 정렬** | 원본 코드 | 비스듬한 부재의 **가장 긴 모서리를 가로로** 맞춰 반듯한 도면을 뽑는 것 (SDK Demo 방식) |
| **벨①·벨②** | **내가 붙인 이름** | SDK 이벤트. 정식으로는 **이벤트 콜백 / 비동기 완료 알림** |

⚠ **줄 세워 돌리기는 「무창」 때문이 아니다** — *"이벤트 콜백 안에서는 SDK IsBusy가 아직 true"* 라서다.
(커밋 `2e61e46 fix: 간섭검사 후속 실행 Busy 대기`)

### Q. X-Ray가 뭐야?

**대상만 진하게, 나머지는 투명하게 보는 모드.** `xraySelectedNodeIndices`가 그 대상 목록이고,
「선택 항목만 보기」(`btnClashShowSelected_Click`)가 채운다.

**작업 범위 판정에 3단계 우선순위로 쓰인다** (`Drawing2D.cs:203`):
```
① xraySelectedNodeIndices 있으면  → 그 목록만
② 없으면                          → Visible == true 인 것
③ 그것도 0건이면                  → 전체
```

📌 `ProcessSingleStruFull`이 `xraySelectedNodeIndices.Clear()` 를 부르는 이유가 이것 —
**②번 「가시성 기준」으로 가게** 만들려고. 두 기준을 섞으면 *"될 때도 있고 안 될 때도 있는"* 버그가 났다.
