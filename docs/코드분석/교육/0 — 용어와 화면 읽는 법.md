## Visual Studio 글자 색깔 — 무슨 뜻인가

VS 어두운 테마 기본값이다. **색 = 그 단어의 "신분"** 이다.

| 색 | 신분 | 예시 | 한 줄 설명 |
|---|---|---|---|
| 🔵 **파란색** | **키워드** | `private` `void` `new` `if` `null` `false` `return` `class` `string` `int` `bool` | C# 언어가 미리 정해둔 단어. 내가 이름으로 못 쓴다 |
| 🟢 **청록/연두** | **타입(클래스·구조체)** | `Panel` `Color` `Label` `Button` `Font` `Size` `Point` `DockStyle` `VIZCore3DControl` | "무엇의 종류". 설계도 이름 |
| 🟡 **노란색** | **메서드(함수)** | `ShowBusyOverlay` `FromArgb` `Add` `Run` `Open` | 부르면 뭔가 하는 것. 뒤에 `( )` 가 붙는다 |
| 🩵 **하늘색** | **변수·필드·파라미터·enum 값** | `message` `busyOverlay` `vizcore3d` `Fill` | 값이 담기는 그릇 |
| ⚪ **흰색/회색** | **속성(프로퍼티)** | `BackColor` `Visible` `Dock` `Controls` `Text` | 그 물건의 성질. `.` 뒤에 오고 `( )` 가 없다 |
| 🟠 **주황/연어색** | **문자열 값** | `"처리 중..."` `"맑은 고딕"` | 따옴표 안의 실제 글자 |
| 🟩 **초록색** | **주석** | `// 이렇게` `/// <summary>` | 사람이 읽는 설명. 실행 안 됨 |

### 헷갈리는 지점 — `string`은 왜 파란색인가

사용자가 `string`·`Color`·`Panel`을 **같은 무리로 봤는데, 그 직관이 맞다.** 셋 다 **타입**이다.
그런데 `string`만 파란색인 건 C#이 `System.String`을 `string`이라는 **키워드 별칭**으로도 쓰게 해줬기 때문이다.
`int`(=`System.Int32`)·`bool`(=`System.Boolean`)도 마찬가지. **의미는 타입, 색은 키워드.**

### 구분 요령 — `( )` 유무

```csharp
busyOverlay.Visible = false;        // ⚪ Visible — 괄호 없음 → 속성 (성질)
busyOverlay.Controls.Add(label);    // 🟡 Add     — 괄호 있음 → 메서드 (동작)
```

## 사용자 질문 기록

### Q. 「필드」가 뭐야?

**클래스가 들고 다니는 변수.** 메서드 안에서만 살다 사라지는 변수(지역 변수)와 달리,
**객체가 살아 있는 내내 남아 있고, 그 클래스의 모든 메서드가 같이 읽고 쓴다.**

```csharp
public partial class Form1
{
    private float _lastModelShiftCanvasX = 0f;   // ← 필드. Form1이 켜져 있는 내내 존재

    private void ShowAllDimensions()
    {
        float baseOffset;                        // ← 지역 변수. 이 함수 끝나면 사라짐
        _lastModelShiftCanvasX = 12.5f;          //   필드는 여기서 써도 다른 함수가 읽는다
    }
}
```

📌 **이 프로그램의 핵심 문제가 여기 있다.** `Form1`은 파일 12개로 나뉘어 있지만 **클래스는 하나**라
필드 **96개**를 12개 파일이 공유한다. 그래서 "파일 열기" 할 때 **23줄을 손으로 `.Clear()`** 해야 한다
(→ [2교시](./2교시%20—%20모델%20열기.md) ②). 리팩토링 「공유 상태 묶기」가 이걸 손보는 것이다.

### Q. 「DataGridView」가 뭐야?

**윈도우 화면에 표(격자)를 그려주는 부품.** 엑셀 시트처럼 행·열이 있다.
`Form1` 생성자의 `SetupAttributeColumns()`가 이 표의 컬럼을 만든다.

이 프로그램의 화면 부품(컨트롤) 종류:

| 부품 | 화면에서 | 코드 이름 예 |
|---|---|---|
| `Button` | 누르는 버튼 | `btnOpen` (「파일 열기」) |
| `ListView` | 목록 (여러 컬럼) | `lvBOM` `lvClash` `lvDimension` |
| `DataGridView` | 표 (편집 가능한 격자) | 부재 정보 탭 |
| `CheckedListBox` | 체크박스 달린 목록 | `clbStruList` (STRU 목록) |
| `Panel` | 다른 부품을 담는 빈 상자 | `panelViewer` (3D 뷰어가 여기 들어감) |
| `Label` | 그냥 글자 | `lblStruTitle` |
| `TextBox` | 입력창 | `txtStruSearch` |

**이름 앞머리로 종류를 안다** — `btn`=버튼, `lv`=ListView, `clb`=CheckedListBox, `lbl`=Label, `txt`=TextBox, `panel`=Panel.

### Q. `busyOverlayCancelButton.Click` — 「Click」은 이벤트인가?

**맞다. 이벤트다.**

```csharp
busyOverlayCancelButton.Click += BusyOverlayCancelButton_Click;
//                       ↑ 이벤트          ↑ 이벤트가 나면 부를 함수
//                          ↑ += "이 함수도 불러줘" 라고 등록
```

**이벤트 = 벨.** "이런 일이 생기면 알려줘"를 등록해두는 자리다. `+=` 는 등록이지 실행이 아니다.
버튼을 누르는 순간 윈도우가 `Click` 이벤트를 울리고, 등록된 함수가 그때 실행된다.

📌 [1교시](./1교시%20—%20켜지는%20순간.md)의 **벨①**(`OnInitializedVIZCore3D`)·**벨②**(`OnClashTestFinishedEvent`)가
정확히 같은 물건이다. 버튼 클릭이든 SDK 준비 완료든 **전부 이벤트**다.

### Q. `VIZCore3D.NET` 이런 건 뭐야?

**네임스페이스(namespace)** — 이름이 겹치지 않게 묶어둔 **폴더** 같은 것이다.

```csharp
VIZCore3D.NET.ModuleInitializer.Run();
└─────┬─────┘ └───────┬───────┘ └┬┘
  네임스페이스        클래스     메서드
   (폴더 경로)       (설계도)    (동작)
```

`.`으로 파고들어 간다. 폴더 경로 `C:\문서\보고서.docx`와 같은 구조다.

파일 맨 위 `using System.Windows.Forms;` 는 **"이 폴더는 매번 안 쓰고 생략하겠다"** 는 선언이다.
그래서 `System.Windows.Forms.Panel` 을 그냥 `Panel` 로 쓸 수 있다.

### Q. 「부모」가 뭔데?

**나를 담고 있는 상자.** `A.Controls.Add(B)` 를 하는 순간 **A가 부모, B가 자식**이 된다.

```csharp
panelViewer.Controls.Add(vizcore3d);
//    ↑ 부모              ↑ 자식
```

`Controls` = "내가 품은 자식 목록", `Add` = 거기 하나 넣기.
**부모는 코드가 정한다.** `Controls.Add` 한 줄을 찾으면 부모가 누군지 알 수 있다.

#### 이 프로그램의 실제 화면 나무

`Form1.Designer.cs`의 `Controls.Add` 를 전부 뽑으면 이렇게 된다:

```
Form1 (창 — 최상위. 부모가 없다)
 └ splitContainer1                         Dock=Fill  ← 창 전체를 좌우로 쪼갬
    ├ Panel1 (왼쪽)
    │   ├ tabControlLeft                   Dock=Fill  ← 「도면」「작업」「부재정보」 탭
    │   │   ├ tabPageDrawing (도면 탭)
    │   │   │   ├ panelDrawingHeader       Dock=Top     ← 제목 줄
    │   │   │   ├ panelDrawingButtons      Dock=Bottom  ← 버튼 7개
    │   │   │   │   └ btnMfgDrawingSheet · btnGenerateSheet2D ·
    │   │   │   │      btnExportFabricationSheets(「제작도」) … 총 7개
    │   │   │   └ splitContainerDrawing    (나머지 공간)
    │   │   │       ├ Panel1 → lvDrawingSheet (도면 목록)
    │   │   │       │        → groupBoxStru
    │   │   │       │             ├ clbStruList          ← STRU 체크 목록
    │   │   │       │             └ panelStruHeader
    │   │   │       │                  ├ btnSelectAllStru
    │   │   │       │                  └ lblStruTitle    ← "STRU 목록 (12개)"
    │   │   │       └ Panel2 → lvDrawingBOMInfo (BOM 표)
    │   │   ├ tabPageWork (작업 탭)
    │   │   └ tabPageAttribute (부재정보 탭)
    │   ├ panelGlobalActions          ← 「파일 열기」 버튼이 여기
    │   └ panelGlobalViewButtons      ← 축 전환 버튼들
    └ Panel2 (오른쪽)
        └ panelViewer                 Dock=Fill
```

**`Form1`만 부모가 없다**(창 자체가 최상위). 나머지는 전부 누군가의 자식.

#### 그래서 Dock이 무슨 뜻이 되나

**"내 부모가 준 공간 안에서 나는 어디에 붙을까".** 같은 부모(`tabPageDrawing`) 안의 세 자식:

| 자식 | Dock | 결과 |
|---|---|---|
| `panelDrawingHeader` | `Top` | **위에** 가로로 쫙 (제목 줄) |
| `panelDrawingButtons` | `Bottom` | **아래에** 가로로 쫙 (버튼 7개) |
| `splitContainerDrawing` | (Fill) | **위아래가 먹고 남은 가운데** 전부 |

📌 **순서가 있다.** `Top`·`Bottom`이 먼저 자기 몫을 떼어가고 `Fill`이 **남은 것**을 가져간다.
그래서 화면이 「제목 / 목록 / 버튼」 세 줄로 나뉜다.

#### Fill 사슬

창을 최대화하면: `splitContainer1`(Fill) → `Panel2` → `panelViewer`(Fill) → `vizcore3d`(Fill)
순으로 전부 따라 커진다. **각 부품은 자기 부모만 신경 쓰면 된다.**

#### 확인해볼 것

`Form1.Designer.cs`에서 **`Controls.Add`** 검색 → 30줄 넘게 나온다. **그 목록이 곧 화면 구조도다.**
`왼쪽.Controls.Add(오른쪽)` 을 "왼쪽이 오른쪽을 품는다"로 읽으면 위 나무가 그대로 나온다.

**버튼의 부모를 찾으면 화면 위치를 안다** — `btnExportFabricationSheets`(「제작도」)는
`panelDrawingButtons`의 자식이고 그건 `Dock=Bottom`이니 **「도면」 탭 맨 아래 버튼 줄**에 있다.

### Q. `DockStyle.Fill` 은? / Q. enum이 뭔데?

**enum = 정해진 선택지 목록.** "이 자리에 올 수 있는 값은 이것들뿐"이라고 못박는 것.

```csharp
vizcore3d.Dock = DockStyle.Fill;
//               └───┬───┘ └┬┘
//            enum 이름(🟢타입) 그중 한 값(🩵)
```

`DockStyle`의 선택지: `None` `Top` `Bottom` `Left` `Right` `Fill`.
`Fill` = "부모가 준 공간을 꽉 채워라" → 3D 뷰어가 `panelViewer` 크기에 딱 맞게 늘어난다.

#### 이 프로젝트가 직접 만든 enum — `Form1.DrawingSheets.cs:1251`

```csharp
private enum DrawingSheetExportKind
{
    Fabrication,     // 제작도
    Assembly,        // 조립도
    Installation     // 설치도
}
```

**왜 만들었나 — 버튼 3개가 같은 함수를 쓰려고.**

```csharp
private void btnExportFabricationSheets_Click(...)   // 「제작도」 버튼
    => ExportSheetsByKind(DrawingSheetExportKind.Fabrication);
private void btnExportAssemblySheets_Click(...)      // 「조립도」 버튼
    => ExportSheetsByKind(DrawingSheetExportKind.Assembly);
private void btnExportInstallationSheets_Click(...)  // 「설치도」 버튼
    => ExportSheetsByKind(DrawingSheetExportKind.Installation);
```

버튼 3개가 **전부 `ExportSheetsByKind` 하나를 부르고 "뭐가 다른지"만 넘긴다.**
enum이 없었으면 거의 같은 함수를 3벌 써야 했다.

**받는 쪽은 `switch`로 갈라진다** (`GetDrawingSheetExportKindLabel`):

```csharp
switch (exportKind)
{
    case DrawingSheetExportKind.Fabrication:  return "제작도";
    case DrawingSheetExportKind.Assembly:     return "조립도";
    case DrawingSheetExportKind.Installation: return "설치도";
    default:                                  return "도면";
}
```

#### enum이 좋은 이유

| | enum 쓰면 | 문자열·숫자 쓰면 |
|---|---|---|
| **오타** | `.Fabricaton` → **컴파일 에러**, 즉시 잡힘 | `"Fabricaton"` → 통과하고 **실행 중 조용히 틀림** |
| **자동완성** | `.` 찍으면 선택지가 뜸 | 문서를 봐야 함 |
| **의미** | `Fabrication` — 읽으면 안다 | `-1` — 뭔지 알 수 없다 |

#### 🔴 반례가 같은 함수 안에 있다 — 매직 넘버

```csharp
private bool MatchesDrawingSheetExportKind(DrawingSheetData sheet, DrawingSheetExportKind exportKind)
{
    switch (exportKind)
    {
        case DrawingSheetExportKind.Fabrication:  return sheet.BaseMemberIndex == -1;
        case DrawingSheetExportKind.Assembly:     return sheet.BaseMemberIndex >= 0;
        case DrawingSheetExportKind.Installation: return sheet.BaseMemberIndex == -2;
    }
}
```

**왼쪽은 enum, 오른쪽은 맨숫자다.** `BaseMemberIndex`가
`-1`=제작도 · `-2`=설치도 · `0 이상`=조립도(그 값이 기준 부재 번호)라는 **약속이 코드에 못박혀 있지 않다.**
이걸 **매직 넘버**라 한다. `-2`를 처음 본 사람은 뜻을 알 수 없고, `-3`을 넣어도 컴파일러가 안 막는다.

> 📌 **enum이 왜 좋은지 알려면 enum을 안 쓴 코드를 보면 되는데, 그게 같은 함수 안에 나란히 있다.**
> 리팩토링에서 손볼 지점.

#### 자주 보이는 enum

| 값 | 어디서 |
|---|---|
| `DockStyle.Fill` | 부품을 부모 공간에 꽉 채우기 |
| `DialogResult.OK` | 파일 선택창에서 확인을 눌렀나 |
| `Object3dFilter.ASSEMBLY` | 나무에서 어셈블리만 골라내기 |
| `ClashTest.ClashTestKind.GROUP_VS_GROUP` | 간섭검사를 그룹 대 그룹으로 |
| `BorderStyle.FixedSingle` | 테두리 한 줄 |
| `MessageBoxIcon.Error` | 오류 창의 빨간 아이콘 |

**앞이 enum 이름(🟢타입), 뒤가 그중 한 값(🩵).** 위 색깔 표와 그대로 이어진다.

### Q. `new VIZCore3DControl()` — 메서드는 아닌 것 같은데?

**생성자(constructor) 호출이다.** `new 타입이름()` = **"이 설계도로 물건을 하나 만들어라".**

```csharp
vizcore3d = new VIZCore3D.NET.VIZCore3DControl();
//          └┬┘ └──────────┬──────────┘└┬┘
//          만들어라      설계도(타입)   생성자 호출
```

📌 **1교시에서 이미 봤다.** `Program.cs`의 `Application.Run(new Form1());` —
`new Form1()`이 바로 이것이다. **창(Form1)을 하나 만들어라.** 만드는 순간 `public Form1() { ... }` 생성자가 실행된다.

`VIZCore3DControl`도 똑같이 만들어지고, 만들어진 물건을 `vizcore3d` **필드**에 담아두기 때문에
이후 모든 파일에서 `vizcore3d.무엇` 으로 쓸 수 있다. (실제로 **826회 / 11개 파일**에서 쓴다.)

### Q. `= "처리 중..."` 처럼 파라미터에 값이 붙어 있는 건?

**기본값(default parameter).** 안 넘기면 이 값을 쓴다.

```csharp
private void ShowBusyOverlay(string message = "처리 중...")

ShowBusyOverlay();                 // → message 는 "처리 중..."
ShowBusyOverlay("도면 생성 중...");  // → message 는 "도면 생성 중..."
```

## 이 프로그램에서 계속 나오는 SDK 용어

| 용어 | 무엇 |
|---|---|
| **Node** | 3D 모델 나무의 한 칸. `ASSEMBLY` / `PART` / `BODY` 세 종류 |
| **STRU** | 도면 한 묶음의 단위. **SDK 개념이 아니라 이 프로그램이 규칙으로 찾아낸 것** |
| **BOM** | 부재 목록표 (Bill Of Materials). 도면 우측에 들어가는 표 |
| **UDA** | 모델에 붙은 사용자 정의 속성 (재질·무게·TAG 등). `UDA.FromIndex(인덱스, 키)` 로 읽는다 |
| **Osnap** | 형상의 특징점 (모서리 끝점·원 중심 등). 치수를 붙일 자리 |
| **체인치수** | 여러 부재를 가로지르며 이어진 치수선 |
| **간섭검사(Clash)** | 두 부재가 겹치거나 가까운지 SDK가 검사. 이 프로그램은 **3mm 근접**으로 쓴다 |
| **viewArea** | 엑셀 템플릿이 지정한 "여기에 모델 그려라" 영역 |
| **X-Ray** | 대상만 진하게, 나머지는 투명하게 보는 모드 |
