## 0. 이 문서를 읽는 법

- **단계 0~4**는 순서가 곧 안전 순서다. 앞 단계일수록 위험이 낮고 되돌리기 쉽다

## 1. 전제와 원칙

| # | 원칙 | 이유 |
|---|---|---|
| P1 | **동작 불변** — 리팩토링 커밋은 기능·출력을 바꾸지 않는다 | 실기 검증이 사내에서만 가능. 동작이 바뀌면 원인 추적 불가 |

## 7. 단계 4 — 상태 묶기 `DrawingJobContext` (진짜 공사, 마일스톤 후보)

**왜 벽인가**: 공유 필드 96개(경계 넘는 것 40개)를 12개 파일이 직접 읽고 쓴다. `vizcore3d` 826회. 나와 Codex가 **서로 다른 각도에서 같은 결론** — Codex는 BOM·Clash·Stru 세 문서에서 *"작업 단위 컨텍스트가 먼저"* 라고 반복했고, 내 Form1 분석의 4단계와 일치한다.

**방향** (실행 계획이 아니라 방향만):

```
Form1 평면 필드 96개
  → ModelSession   (모델·경로·Body/Part 맵·모델 수명 캐시)     ← 모델 교체 시 일괄 무효화
  → DrawingJob     (bomList·clashList·osnap·치수·시트 — 한 번의 추출~출력 작업 단위)
  → ViewState      (X-Ray 선택·풍선·카메라 잔존값)
```

**착수 조건 제안** — 🔲 D5: 단계 0~2가 끝나 있고 + 실기 여유가 2주 이상 있을 때 (신규 API 9건 반영 일정과 겹치지 않게). 단계 2c의 어댑터들이 사실상 이 단계의 뼈대가 된다.

## 7-1. 클래스 분리 착수 순서 (2026-08-31 실측 기반)

**공유 필드를 몇 개 쓰느냐**로 난이도가 갈린다. 쉬운 것부터 해서 **방법이 통하는지 먼저 확인**한다.

| 순서 | 대상 | 줄 | 쓰는 공유 필드 | 난이도 |
|---|---|---|---|---|
| **①** | `Attribute.cs` → `AttributePanel` | 618 | **2개** (`selectedAttributeNodeIndex` · `vizcore3d`) | **가장 쉬움** |
| ② | `Drawing2D.cs`의 PDF 페이지 관리 → `PdfPageWriter` | 237 | 적음. `Begin…`/`End…`/`Flush…`로 경계가 이미 섬 | 쉬움 |
| ③ | `GlobalViews.cs`의 설치도 계산 → `InstallationLayout` | 960 | `bomList`·`clashList`·`bodyToPartIndexMap` 등 | 중간 |
| ④ | `Clash.cs`의 BOM 표 조립 → `DrawingBom` | 532 | UDA 일원화(2c)와 함께 | 중간 |
| ⑤ | `Dimensions.cs`의 순수 계산 792줄 → `Core` | 792 | 파라미터화 필요 | 어려움 |

**①이 본보기다** — 밖에서 이 파일을 부르는 게 **0건**이고, 도면 파이프라인 필드를 **하나도 안 쓴다**.
끊을 실은 `selectedAttributeNodeIndex` 하나 + `SetupAttributeColumns`(3-5) 가져오기뿐.

⚠ ①을 뗄 때 알 것: **이 탭은 모델을 실제로 고친다**(`UDA.Add/Update/Delete` 5곳).
코드는 남남이지만 **데이터로는 도면과 이어져 있다**(고친 UDA가 BOM 표·표제부에 실림).

## 7-2. 안전망 — 테스트 프로젝트 (리팩토링 착수 전)

**지금은 "동작 불변"을 사람이 도면 뽑아 눈으로 확인한다.** 느리고 놓치기 쉽다.

```
A2Z.sln
  ├ A2Z.csproj          제품 (그대로)
  └ A2Z.Tests.csproj    테스트 — 제품에 안 들어감
```
`AssemblyInfo.cs` 에 `[assembly: InternalsVisibleTo("A2Z.Tests")]` 한 줄.

**무엇을 테스트하나** — 순수 계산 98개(1,758줄, 전체의 12%) 중 **5~10개면 충분**:

| 우선 | 함수 | 왜 |
|---|---|---|
| 1 | `IsSingleConnectedComponent` (Clash, 75) | **틀리면 도면이 아예 안 나온다** |
| 2 | `ApplySmartFiltering` (Dimensions, 132) | 규칙이 가장 복잡 |
| 3 | `MergeShortDimensions` (Dimensions, 63) | 병합 규칙 |
| 4 | `MergeConnectedContactSegments` (GlobalViews, 24) | 1mm 묶기 |
| 5 | `ToAlphabeticLabel` (GlobalViews, 12) | A~Z·AA 경계 |

⚠ **대부분 필드를 직접 읽어 지금은 테스트 불가.** 파라미터로 받게 바꾸는 **「순수 함수 승격」이 선행**된다
(본문 로직은 그대로, 필드명 → 파라미터명으로 교체 + `static`).

📌 **리팩토링에서는 「지금 나오는 값」이 정답**이다. 사양을 몰라도 **현재 동작을 박제**하면 된다
(characterization test). 러너가 실제 값을 알려주므로 아무 값이나 넣고 한 번 돌리면 채워진다.

⚠ 테스트가 커버하는 건 **12%**. SDK가 그리는 도면은 여전히 실기로만 확인 가능하다.
