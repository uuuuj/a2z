목적 순위에 따라 같은 재료의 우선순위가 달라진다.

| 목적이 이것이라면 | 우선할 단계 | 이유 |

## 7. 단계 4 — 상태 묶기 `DrawingJobContext` (진짜 공사, 마일스톤 후보)

**왜 벽인가**: 공유 필드 96개(경계 넘는 것 40개)를 12개 파일이 직접 읽고 쓴다. `vizcore3d` 826회. 나와 Codex가 **서로 다른 각도에서 같은 결론** — Codex는 BOM·Clash·Stru 세 문서에서 *"작업 단위 컨텍스트가 먼저"* 라고 반복했고, 내 Form1 분석의 4단계와 일치한다.

**방향** (실행 계획이 아니라 방향만):

```
Form1 평면 필드 96개
  → ModelSession   (모델·경로·Body/Part 맵·모델 수명 캐시)     ← 모델 교체 시 일괄 무효화
  → DrawingJob     (bomList·clashList·osnap·치수·시트 — 한 번의 추출~출력 작업 단위)
  → ViewState      (X-Ray 선택·풍선·카메라 잔존값)
```

**착수 조건 제안** — 🔲 D5: 단계 0~2가 끝나 있고 + 실기 여유가 2주 이상 있을 때 (신규 API 9건 반영 일정과 겹치지 않게). 단계 2c의 어댑터들이 사실상 이 단계의 뼈대가 된다.


**"1만 줄" 지적에 대한 답은 줄 수가 아니다.** 조사 결과로 말할 수 있는 논리:

> 죽은 코드와 중복을 걷어내면 약 19,000줄. 그중 SDK 우회가 6계열(벤더 한계 — 트랙 A로 회수 예정), 나머지는 **도면 규칙 계산**(치수 선별·배치·시트 분할·EA 처리·접합 판정)이다. 이 계산들이 이 프로그램의 실체이며, 문서 13개의 5절이 그 목록이다.
