## Claude의 사전 검토 발견 (Codex가 검증해야 할 핵심)

**[A1 - 빌드 차단 위험 - 즉시 v3 패치 필요]**
v2 §3 P2b의 `EnsureViewAreasCache` 시그니처는 `Dictionary<string, TemplateViewArea>` (key="View_1" 등)를 명시하지만, VIZCore3D.NET.xml과 실제 코드(Form1.DrawingSheets.cs:1809, Form1.ExcelTemplate.cs:124)에서 확인한 결과:
- `TemplateViewArea.Index` 타입은 **int** (xml 명시: "{View_n}의 n")
- 코드에서 이미 `Dictionary<int, CameraDirection>` + `cameraMap.TryGetValue(p.Index, ...)` 패턴 사용 중
- v2 계획서대로 `cache.ToDictionary(a => a.Index, a => a)` + `cache[$"View_{i+1}"]` 작성 시 **컴파일 에러** (string → int 키 변환 불가)
→ 권고: v3에서 `Dictionary<int, TemplateViewArea>` + `cache[i + 1]` 로 정정

**[A2 - 정책 모순]**
v2 §3 P2d btnMfgDrawingSheet_Click 재배선: `string saveDir = Path.Combine(GetSolutionPath(), "Drawings")` 명시.
하지만 자동 STRU 일괄 (Form1.Stru.cs:362)은 `Path.Combine(Application.StartupPath, "Drawings")` 사용 — 두 경로가 다름:
- GetSolutionPath() = `C:\...\a2z\` (.sln 위치)
- Application.StartupPath = `C:\...\a2z\A2Z\bin\Debug\` 또는 `Release\`
v2가 "§3 P2d T-064 정책 일치"라고 진술했으나 실제로는 불일치.
→ 권고: 자동과 동일하게 Application.StartupPath 사용하거나, 양쪽 모두 GetSolutionPath()로 통일 (사용자 결정 필요)

**[A3 - 함수 중복 vs helper 분리 트레이드오프]**
v2 P2a의 ParseSprefForMfgRow는 CollectBOMInfo (Form1.Clash.cs:86~) SPREF/MATREF/POSSTART/POSEND/GWEI 부모 10단계 탐색 로직을 추출하는데:
- 현재 CollectBOMInfo는 udaKeyList를 외부 한 번 캐시 후 partNodes 루프 안에서 사용
- helper로 추출하면 BOM 1개당 udaKeyList 한 번씩 새로 가져오게 됨 (성능 저하 N×UDA.Keys 호출)
- 가공도 행 5개 × STRU 다수 → 명시적 캐싱 누락 시 측정 가능한 지연
→ 권고: helper 시그니처에 `List<string> udaKeyList = null` 옵션 추가, 호출자가 한 번 가져온 키 목록 전달 가능하게

**[B1 - commit 분할 입도]**
v2 §3 P2a~P2d 4개 commit이 모두 "호출자 0건 → 빌드 green" 으로 끝나는데, P2d 진입 전까지 사용자가 사내 검증을 할 수 없음. P2a~P2c는 정말 합쳐도 무방한지, 아니면 분할이 코드 리뷰·롤백 단위로 가치 있는지 의문.
→ 의견 요청: 사용자 1인 개발 + 작은 팀 환경에서 4 commit 분할이 과한지

**[C1 - 명확성 - 사용자 시점]**
§6 작업 순서 다이어그램이 명확하지만, 사용자가 P3 사내 검증 진입 시 "P2d 직후 어디서 어떤 PDF를 검증하면 되는가" 가 §3 P3에 일부 설명 있으나 흐름이 작업/데이터 탭 buttons 폐기 + 도면정보 탭 가공도 버튼이라는 점이 다른 부분과 분리돼 있어 사용자 혼동 가능
→ 권고: §6 다이어그램 옆에 "수동 진입점: 도면정보 탭 > '가공도 출력' 큰 버튼" 한 줄 추가

**[D1 - RenderMfgRowToViewArea 반환값 처리]**
v2 §3 P2c가 bool 반환을 명시했으나 §3 P2d의 GenerateMfgDrawingManual 호출부에서 그 반환값을 무시 (`RenderMfgRowToViewArea(i + 1, bom, area);`)
- 일부 row 실패 시 페이지 전체 export 진행? 빈 영역 그대로 PDF 저장됨
- 사용자가 "5부재 중 3개만 그려진 PDF"를 받아도 알 방법 없음
→ 권고: 실패 row 카운트 누적 + DiagLog + export 직전 if (실패 row > 0) MessageBox warning, 또는 page-skip 정책 명시

**[D2 - v2.1 (parent) 충돌 가능성]**
v2.1 parent 문서가 EA 두 뷰 분기를 §4.6에 가지고 있고 G2-b/G2-c baseline 게이트 요구. v2가 EA를 P5로 미루면서 baseline 게이트 명시 없음 — parent 의도 vs v2 진행 안 충돌?
→ 의견 요청
